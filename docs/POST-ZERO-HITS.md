# Semgrep's official AI rule pack finds zero bugs in TypeScript

> Draft writeup. The empirical backing, including the other tools surveyed, is
> in [`COMPETITIVE-LANDSCAPE.md`](COMPETITIVE-LANDSCAPE.md). Publish as a blog
> post, a dev.to article, or an OWASP / Semgrep community post.

Semgrep ships an official rule pack for AI application security:
`p/ai-best-practices`. Twenty-seven rules, maintained by Semgrep, covering
prompt injection, agent loops, MCP server configuration, and Claude Code hook
scripts. If you are building an LLM feature and you reach for one thing, it is
the obvious thing to reach for.

Run it against a TypeScript codebase and it returns nothing. Not "no issues
found" — nothing scanned at all.

```
Rules run: 27
Targets scanned: 0
Findings: 0
```

That is not a bug. It is a language coverage boundary that nobody states out
loud, and it matters because a green scan reads identically either way.

## Where the 27 rules actually point

Downloading the pack and grouping every rule by its `languages:` declaration:

| Languages targeted | Count | What they cover |
|---|---|---|
| Python | 13 | LangChain, and the OpenAI / Anthropic / Cohere / Gemini / Mistral / HuggingFace **Python** clients, agent unbounded loops, MCP servers written in Python |
| Generic (regex over any text) | 11 | MCP server config, Claude Code `settings.json`, hidden Unicode, IDE settings |
| Bash | 3 | Claude Code hook scripts — unquoted vars, `wget \| bash`, DNS exfiltration |
| **JavaScript / TypeScript** | **0** | Nothing |

Semgrep filters targets by language before scanning. With no rule declaring
`javascript` or `typescript`, every `.ts` and `.tsx` file is excluded up front.
The scan completes successfully, exits 0, and reports zero findings — the same
output a genuinely clean codebase produces.

Verify it yourself:

```sh
curl -s https://semgrep.dev/c/p/ai-best-practices > /tmp/pack.yaml
grep -A2 "^\s*languages:" /tmp/pack.yaml | grep -E "^\s*-\s+" | sort | uniq -c
```

## Why this is a real gap and not a nitpick

The LLM application ecosystem is not Python-only, and arguably is not
Python-first. The Vercel AI SDK, the OpenAI and Anthropic JS SDKs, Next.js
route handlers, Server Actions, and AI Gateway are where an enormous amount of
LLM-integrated code is being written right now — much of it generated by AI
coding assistants that reproduce the same insecure shapes over and over:

- user input dropped into the `system` role, because the assistant read the
  user's "instructions" as instructions
- `JSON.parse` on model output with no schema between the model and the
  property access
- retrieved documents concatenated into `system`, which is indirect prompt
  injection with extra steps
- a streaming handler with no `abortSignal`, which bills tokens for a response
  nobody is still reading
- a tool name from the model used to index a handler map, with no allowlist

None of these are exotic. All of them are TypeScript. None are covered.

## What I built

[`llm-audit`](https://github.com/Javierlozo/llm-audit) is a Semgrep rule pack
and CLI for exactly that gap: twelve rules, TypeScript / TSX / JavaScript,
each mapped to an OWASP LLM Top 10 entry, each shipping with a vulnerable
fixture *and* a safe fixture that must produce zero findings.

Same fixture set, same machine:

| | `llm-audit` | `p/ai-best-practices` |
|---|---|---|
| JS/TS rules | 12 | 0 of 27 |
| Findings on the TS/TSX fixtures | 40 | 0 |
| False positives on the safe fixtures | 0 | n/a |

```sh
git clone https://github.com/Javierlozo/llm-audit.git && cd llm-audit
semgrep --config p/ai-best-practices test/fixtures/ --metrics=off   # 0 targets
npm test                                                            # 12 rules, 42 matches
```

## The honest framing

This is not a category-creating product, and `p/ai-best-practices` is not bad
work — it is good work with a stated language scope that people do not read.
`llm-audit` is the TypeScript half of the same story. Run both. In a polyglot
repo they do not overlap at all, which is the whole point.

If Semgrep adds JS/TS rules to the upstream pack, this post stops being true,
and I will say so.
